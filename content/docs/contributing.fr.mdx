# Contribuer à la documentation technique

Chaque titre de page et en-tête de section modifiable est doté d'un crayon subtil. Le sélectionner ouvre le fichier Markdown ou MDX correspondant sur la ligne exacte dans l'éditeur Web de GitHub sur `main`.

## Effectuer une modification rapide

1. Sélectionnez le crayon à côté du titre de la page ou de la section que vous souhaitez améliorer.
2. Connectez-vous à GitHub si vous y êtes invité.
3. Modifiez la source en surbrillance. Si vous n'avez pas d'accès en écriture, GitHub crée automatiquement un fork pour vous.
4. Sélectionnez **Proposer des modifications**, décrivez l'amélioration et ouvrez une demande d'extraction dans `main`.
5. Laissez la validation du contenu public se terminer et répondez aux commentaires du responsable.

Après approbation, l'automatisation synchronise le contenu identique en octets dans le référentiel d'application privé et le site rendu est déployé via la piste de publication normale. Les validations marquées `[docs-sync]` sont ignorées par le flux de travail réciproque, de sorte que le miroir bidirectionnel ne peut pas effectuer de boucle.

Les tâches de synchronisation comparent les hachages de l'arborescence de contenu Git après chaque transfert. Cela maintient les fichiers publics `main` identiques en octets à la source rendue afin qu'un lien d'édition ne puisse pas dériver silencieusement vers la mauvaise ligne.

L'application, le moteur de rendu Fumadocs, l'implémentation de l'API, les paramètres de déploiement et les informations d'identification restent dans le référentiel d'application privé. Les pages d'opération d'API individuelles sont générées à partir du document Dashboard OpenAPI, elles fournissent donc un lien **Signaler un problème de documentation d'API** au lieu d'un crayon de ligne source trompeur.

## Écrivez une contribution utile

- Nommez le produit pris en charge, la révision matérielle, la version du micrologiciel ou le schéma API lorsque cela est important.
- Liez les réclamations techniques à la mise en œuvre ou à la spécification utilisée pour les vérifier.
- Conservez les images à côté de la page qui les utilise et vérifiez chaque chemin relatif.
- Réutilisez les légendes, cartes, onglets, accordéons et étapes MDX existants.
- Gardez chaque demande d'extraction ciblée et n'incluez jamais d'informations d'identification, d'informations privées sur le produit ou de sortie de build générée.

Les petites corrections peuvent être effectuées entièrement dans GitHub. Pour des modifications plus importantes, dupliquez et clonez le référentiel public, modifiez son arborescence `content/` et utilisez l'extension Fumadocs Preview pour VS Code avant d'ouvrir la demande d'extraction.
