# RAD BLE v1 namespaces

RAD BLE v1 gives OSSM, RADR, DTT, and LKBX the same control language while
keeping each product in a distinct GATT service namespace. Clients can use one
set of characteristic suffixes and request operations without confusing one
product for another.

<Info>
  The service UUID identifies the product. The advertised device name is
  customizable and must never be used as product identity.
</Info>

## Product service namespaces

Each product owns one 128-bit primary service UUID. The `0001` group marks the
service root.

| Device | Product token        | Primary service UUID                   |
| ------ | -------------------- | -------------------------------------- |
| OSSM   | `4f53-534d` (`OSSM`) | `522b443a-4f53-534d-0001-420badbabe69` |
| RADR   | `5241-4452` (`RADR`) | `522b443a-5241-4452-0001-420badbabe69` |
| DTT    | `4454-5400` (`DTT`)  | `522b443a-4454-5400-0001-420badbabe69` |
| LKBX   | `4c4b-4258` (`LKBX`) | `522b443a-4c4b-4258-0001-420badbabe69` |

To construct a characteristic UUID, keep the product token and replace the
service-root suffix `0001` with the characteristic suffix.

```text
service:        522b443a-4f53-534d-0001-420badbabe69
request (1000): 522b443a-4f53-534d-1000-420badbabe69
state (2000):   522b443a-4f53-534d-2000-420badbabe69
```

The same `1000` suffix in the DTT namespace is
`522b443a-4454-5400-1000-420badbabe69`. UUID comparison is case-insensitive,
but examples and generated constants use lowercase.

## Characteristic range map

Suffix families describe the kind of traffic. Only the assignments listed
below are part of v1; unassigned suffixes in a family are reserved.

| Suffix family | Purpose                                   | Typical actions                                                                                              |
| ------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `0000–0fff`   | Discovery, identity, and catalog metadata | Identify the protocol/device, discover resources, read or change the display name                            |
| `1000–1fff`   | Correlated command transactions           | Acquire a lease, read/write settings and sensors, select targets, configure Wi-Fi, restart                   |
| `2000–2fff`   | State, events, and high-rate telemetry    | Subscribe to device state, essential live state, events, or binary streams                                   |
| `3000–3fff`   | Inputs and sensors                        | Observe or inject buttons/encoders; subscribe to IMU, power, analog, magnetic, motion, and connectivity data |
| `4000–4fff`   | Outputs and user feedback                 | Set indicators, haptics, audio, or display output                                                            |
| `5000–5fff`   | Direct update transport                   | Start, transfer, resume, finish, abort, and monitor application/filesystem updates                           |
| `6000–ffff`   | Reserved                                  | Future protocol expansion; clients must not infer behavior                                                   |

### Core control and telemetry

These characteristics exist on every RAD BLE v1 device.

| Suffix | Name                 | Properties                    | Use                                                                                      |
| ------ | -------------------- | ----------------------------- | ---------------------------------------------------------------------------------------- |
| `0002` | Protocol Info        | Read                          | Protocol/library version, product service, enabled-channel mask, limits, and OTA support |
| `0003` | Capability Catalog   | Read                          | First catalog page and resource discovery entry point                                    |
| `0004` | Device Name          | Read, Write, Notify           | Read or change the persisted user-facing name                                            |
| `0005` | Device Identity      | Read                          | Manufacturer, model, serial, firmware/build, hardware, and flash size                    |
| `1000` | Request              | Write, Write Without Response | Send JSON operations with a non-zero request ID                                          |
| `1100` | Response             | Read, Indicate                | Receive `accepted`, `progress`, `completed`, or `failed` stages                          |
| `2000` | State                | Read, Notify                  | Full state snapshot on change and a one-second heartbeat                                 |
| `2010` | Essential Live State | Read, Notify                  | Compact user-facing state; the default subscription for integrations                     |
| `2100` | Event                | Read, Notify                  | State transitions and device events                                                      |

The request/response pair is the canonical action path. Mutations require a
lease acquired with `control.acquire`. A response with `stage: "accepted"`
confirms queuing, not completion; wait for `completed` or `failed`, then use
State or Essential Live State as the authoritative result.

### Optional channel assignments

Optional channels are created only when enabled by that firmware build.
Protocol Info reports a numeric `channels` mask. The bit and hexadecimal mask
below let clients interpret it.

| Channel name     | Bit / mask    | Suffix or standard UUID               | Properties          | Action/data category                                                   |
| ---------------- | ------------- | ------------------------------------- | ------------------- | ---------------------------------------------------------------------- |
| `sensorStream`   | 0 / `0x0001`  | `2300`                                | Read, Notify        | Scheduled binary sensor frames configured with `stream.*` operations   |
| `button`         | 1 / `0x0002`  | `3000`                                | Read, Write, Notify | Button state and `input.emit` injection                                |
| `encoder`        | 2 / `0x0004`  | `3010`                                | Read, Write, Notify | Encoder state, `encoder.set`, and `encoder.delta`                      |
| `imu`            | 3 / `0x0008`  | `3100`                                | Read, Notify        | Acceleration, rotation, orientation, or temperature resources          |
| `power`          | 4 / `0x0010`  | `3110`                                | Read, Notify        | Voltage, current, charging, USB, and powered state                     |
| `analog`         | 5 / `0x0020`  | `3120`                                | Read, Notify        | Analog inputs and calibrated distance/value sensors                    |
| `magnetic`       | 6 / `0x0040`  | `3130`                                | Read, Notify        | Hall, TMR, paddle, and lock-position sensors                           |
| `motion`         | 7 / `0x0080`  | `3140`                                | Read, Notify        | Position, velocity, targets, grade, and motion/session data            |
| `connectivity`   | 8 / `0x0100`  | `3150`                                | Read, Notify        | BLE, Wi-Fi, MQTT, peer count, identity, and RSSI state                 |
| `indicator`      | 9 / `0x0200`  | `4000`                                | Read, Write, Notify | LEDs and other visual indicators via `indicator.set`/`output.*`        |
| `haptic`         | 10 / `0x0400` | `4010`                                | Read, Write, Notify | Vibration/reward/punishment outputs via `haptic.set`/`output.*`        |
| `audio`          | 11 / `0x0800` | `4020`                                | Read, Write, Notify | Buzzer or audio feedback via `audio.set`/`output.*`                    |
| `display`        | 12 / `0x1000` | `4030`                                | Read, Write, Notify | Backlight/display feedback via `display.set`/`output.*`                |
| `battery`        | 13 / `0x2000` | Service `180f`, characteristic `2a19` | Read, Notify        | Standard battery percentage; richer values remain in `power` and state |
| `applicationOta` | 14 / `0x4000` | `5000`, `5010`, `5020`                | Mixed               | Application update control, binary data, and status                    |
| `filesystemOta`  | 15 / `0x8000` | Reuses `5000`, `5010`, `5020`         | Mixed               | Enables `filesystem` as an OTA component; requires `applicationOta`    |

Writes to Button, Encoder, Indicator, Haptic, Audio, and Display are convenient
channel-specific forms of the same adapter operations available through
Request. Read-only sensor channels never accept writes. Use the Capability
Catalog to discover exact paths, types, units, ranges, state guards, and lease
requirements instead of guessing them from a channel name.

OSSM deliberately omits the optional JSON surface characteristics to conserve
GATT resources while retaining the shared Request, Response, State, Essential
Live State, Event, Sensor Stream, and application OTA channels. Its full
control and sensor inventory is still available through the catalog and
request operations. DTT provisioning builds omit Motion and Haptic. RADR only
creates IMU when that hardware is available at runtime.

## Routing actions to channels

| Action family                                    | Send/read through                                                                | Observe completion or change through                                     |
| ------------------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Discover capabilities and paths                  | Protocol Info `0002`, Catalog `0003`, or `catalog.*` on Request `1000`           | Response `1100`                                                          |
| Acquire, renew, or release control               | `control.*` on Request `1000`                                                    | Response `1100`; lease state in `2000`                                   |
| Read sensors/settings                            | `sensor.*`, `setting.read`, or `state.read` on Request `1000`                    | Response `1100`; optional `3xxx` surface notifications                   |
| Mutate settings or choose a state-machine target | `setting.*`, `target.set`, `session.apply`, or `state.request` on Request `1000` | Response `1100`, then State `2000`, Essential `2010`, or Event `2100`    |
| Inject a button or encoder action                | Request `1000`, or Button `3000` / Encoder `3010` when present                   | Response `1100` and the relevant state/event notification                |
| Drive feedback outputs                           | Request `1000`, or the matching `4000–4030` channel when present                 | Response `1100` and matching output notification                         |
| Configure Wi-Fi or restart                       | `wifi.*` or `system.restart` on Request `1000`                                   | Response `1100`, Connectivity `3150`, State `2000`, or disconnect/reboot |
| Start or change high-rate telemetry              | `stream.start`, `stream.update`, `stream.stop` on Request `1000`                 | Response `1100`; binary frames on Sensor Stream `2300`                   |
| Transfer an update                               | OTA Control `5000` and OTA Data `5010`                                           | OTA Control indications and OTA Status `5020` notifications              |

## Standard services

RAD BLE devices also expose the Bluetooth SIG Device Information Service
`180a`, including manufacturer `2a29`, model `2a24`, serial `2a25`, firmware
revision `2a26`, hardware revision `2a27`, and software/build revision `2a28`.
Devices with the `battery` channel expose Battery Service `180f` and Battery
Level `2a19`.

## Recommended discovery flow

1. Scan for all four product service UUIDs.
2. Connect and read Protocol Info `0002`; verify both `deviceType` and
   `serviceUuid`.
3. Read Device Identity `0005` for firmware, build, hardware, and physical
   flash details.
4. Subscribe to Essential Live State `2010` and Event `2100`.
5. Read the Capability Catalog before presenting controls.
6. Subscribe only to optional channels present in the GATT table and enabled
   by the channel mask.
7. Acquire a lease immediately before a mutation, send a unique request ID,
   and wait for its terminal response.

The public [RAD BLE library and machine-readable
contract](https://github.com/researchanddesire/rad-ble) are the authoritative
source for generated constants. Pin a released version rather than copying
UUIDs into a client by hand.
