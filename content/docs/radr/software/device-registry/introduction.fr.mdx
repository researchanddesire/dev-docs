title: "Registre des appareils"
description: "Comment RADR découvre et crée des instances de périphérique à partir des UUID du service BLE"
---

Le registre des appareils est le système principal qui mappe les UUID du service Bluetooth Low Energy (BLE) aux usines d’appareils. Lorsque RADR recherche des appareils, il utilise les UUID de service pour déterminer quelle usine doit créer l’instance de périphérique.

## Présentation de l'architecture

RADR utilise un système de registre à deux niveaux :

| Étage | Description | Exemple |
|------|-------------|---------|
| Codé en dur | Appareils enregistrés directement dans le code auprès des usines personnalisées | OSSM |
| Dynamique | Appareils chargés depuis `registry.json` à l'aide de l'usine ButtplugIO | Lovense, Satisfyer, Kiiroo |

```
┌─────────────────────────────────────────────────────────────┐
│                    Device Registry                          │
│                                                             │
│  ┌─────────────────────┐    ┌─────────────────────────────┐│
│  │   Hardcoded Devices │    │      Dynamic Devices        ││
│  │   (Custom Factory)  │    │   (ButtplugIOFactory)       ││
│  │                     │    │                             ││
│  │  Service UUID →     │    │  registry.json →            ││
│  │  Lambda → Device    │    │  Service UUID →             ││
│  │                     │    │  Spec files → Device        ││
│  └─────────────────────┘    └─────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
```

Le registre est renseigné une fois au démarrage de l'appareil via `initRegistry()`.

## Structure du registre

Le registre est une carte globale qui associe les UUID de service aux fonctions d'usine :

```cpp
std::unordered_map<std::string, DeviceFactory> registry;
```

Où `DeviceFactory` est défini comme :

```cpp
typedef Device *(*DeviceFactory)(const NimBLEAdvertisedDevice *advertisedDevice);
```

### Fonctions clés

| Fonction | But |
|----------|---------|
| `initRegistry()` | Remplit le registre avec des appareils codés en dur et dynamiques |
| `getDeviceFactory()` | Recherche une usine par service UUID |

## Appareils codés en dur

Les appareils codés en dur sont enregistrés directement dans `initRegistry()` auprès d'une usine lambda. Cette approche est utilisée pour les appareils dotés de protocoles personnalisés qui nécessitent une gestion spécialisée.

### Exemple OSSM

```cpp
registry.emplace(
    OSSM_SERVICE_ID,  // "522B443A-4F53-534D-0001-420BADBABE69"
    [](const NimBLEAdvertisedDevice *advertisedDevice) -> Device * {
        return new OSSM(advertisedDevice);
    });
```

L'OSSM utilise un protocole BLE personnalisé avec de multiples caractéristiques pour la vitesse, la profondeur, la sensation et le contrôle des coups. Cela nécessite une classe de périphérique dédiée plutôt que l'implémentation générique de ButtplugIO.

### Quand utiliser l’enregistrement codé en dur

Utilisez l'enregistrement codé en dur lorsque :

- L'appareil utilise un protocole personnalisé non couvert par Buttplug.io
- Vous avez besoin d'une interface utilisateur spécialisée ou d'une logique de contrôle
- L'appareil nécessite une manipulation caractéristique unique

## Appareils dynamiques (ButtplugIO)

Les périphériques dynamiques sont chargés à partir du fichier `data/registry.json` sur le système de fichiers. Cela permet d'ajouter la prise en charge de nouveaux appareils sans modifier le code.

### Structure du registre.json

Le registre mappe les UUID du service sur des tableaux de fichiers de spécifications de protocole :

```json
{
  "0000fff0-0000-1000-8000-00805f9b34fb": ["/protocols/lovense.json"],
  "88f80580-0000-01e6-aace-0002a5d5c51b": ["/protocols/kiiroo-v2.json"],
  "51361500-c5e7-47c7-8a6e-47ebc99d80e8": ["/protocols/satisfyer.json"]
}
```

Chaque entrée mappe un UUID (clé) de service BLE à un ou plusieurs fichiers de spécification de protocole (tableau de valeurs).

### Flux d'usine

Lorsqu'un appareil avec un UUID de service enregistré est découvert :

1. `ButtplugIODeviceFactory` lit `registry.json` depuis LittleFS
2. Récupère la liste des fichiers de spécifications pour le service UUID
3. Pour chaque fichier de spécifications :
   - Charge et analyse la configuration JSON
   - Fait correspondre le nom de l'appareil annoncé aux modèles `communication[0].btle.names`
   - Extrait les caractéristiques TX/RX pour l'UUID du service
4. Crée une instance `LovenseDevice` avec la configuration correspondante

### Format de fichier de spécifications de protocole

Les fichiers de spécifications suivent le format Buttplug.io v4 :

```json
{
  "defaults": {
    "name": "Lovense Device",
    "features": [...]
  },
  "configurations": [
    {
      "identifier": ["B"],
      "name": "Max",
      "features": [...]
    }
  ],
  "communication": [{
    "btle": {
      "names": ["LVS-*", "LOVE-*"],
      "services": {
        "0000fff0-0000-1000-8000-00805f9b34fb": {
          "tx": "0000fff2-0000-1000-8000-00805f9b34fb",
          "rx": "0000fff1-0000-1000-8000-00805f9b34fb"
        }
      }
    }
  }]
}
```

| Champ | But |
|-------|---------|
| `defaults` | Nom de l'appareil par défaut et ensemble de fonctionnalités |
| `configurations` | Variantes et identifiants spécifiques à l'appareil |
| `communication[].btle.names` | Modèles de nom de périphérique (prend en charge le caractère générique `*`)  |
| `communication[].btle.services` | UUID caractéristiques TX/RX par service |

## Flux de découverte de périphérique

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  BLE Scan    │────▶│  Get Service │────▶│  Lookup in   │────▶│   Factory    │
│  Discovers   │     │    UUID      │     │   Registry   │     │   Creates    │
│   Device     │     │              │     │              │     │   Device     │
└──────────────┘     └──────────────┘     └──────────────┘     └──────────────┘
```

1. **Scan** : analyse RADR pour les appareils BLE
2. **Extraire l'UUID** : obtient l'UUID du service annoncé
3. **Recherche dans le registre** : `getDeviceFactory(serviceUUID)` trouve l'usine
4. **Créer un appareil** : Factory instancie la classe d'appareil appropriée

## Ajout de la prise en charge d'un nouveau périphérique

### Option A : dynamique (registre Buttplug.io)

Pour les appareils compatibles avec le protocole Buttplug.io :

<Steps>
<Step title="Obtenir ou créer le fichier de spécifications">
Obtenez la spécification du protocole Buttplug.io v4 pour l'appareil. Ceux-ci sont disponibles dans le [référentiel de configuration du périphérique Buttplug](https://github.com/buttplugio/buttplug) .
</Step>

<Step title="Ajouter un fichier de spécifications aux protocoles">
Placez le fichier de spécifications JSON dans `data/protocols/` :
```
data/protocols/your-device.json
```
</Step>

<Step title="Mettre à jour le registre.json">
Ajoutez le mappage UUID du service à `data/registry.json` :
```json
{
  "your-service-uuid": ["/protocols/your-device.json"]
}
```
</Step>

<Step title="Télécharger le système de fichiers">
Utilisez PlatformIO pour télécharger le système de fichiers sur l'appareil.
</Step>
</Steps>

### Option B : codé en dur (protocole personnalisé)

Pour les appareils nécessitant une gestion de protocole personnalisée :

<Steps>
<Step title="Créer une classe d'appareil">
Créez une nouvelle classe d'appareils dans `src/devices/` qui étend la classe de base `Device`.
</Step>

<Step title="Mettre en œuvre les méthodes requises">
Implémentez `getServiceUUID()`, `getName()` et toute logique de contrôle spécifique à l'appareil.
</Step>

<Step title="S'inscrire dans initRegistry">
Ajoutez le code d'enregistrement dans `initRegistry()` :
```cpp
registry.emplace(
    YOUR_SERVICE_UUID,
    [](const NimBLEAdvertisedDevice *adv) -> Device * {
        return new YourDevice(adv);
    });
```
</Step>

<Step title="Reconstruire le micrologiciel">
Compilez et flashez le firmware mis à jour.
</Step>
</Steps>

## Flux de travail de développement

### Mise à jour du registre (développement)

Lors du développement local, utilisez la fonctionnalité « Télécharger le système de fichiers » de PlatformIO pour flasher le répertoire `data/` sur LittleFS :

1. Modifiez `data/registry.json` ou ajoutez des fichiers de spécifications à `data/protocols/`
2. Dans VS Code avec PlatformIO, cliquez sur **Télécharger le système de fichiers** (ou exécutez `pio run --target uploadfs`)
3. L'appareil utilisera le registre mis à jour au prochain démarrage

<Warning>
"Upload Filesystem" efface la partition LittleFS existante avant l'écriture. Toutes les modifications d'exécution seront perdues.
</Warning>

### Mise à jour du registre (production)

<Info>
Les mises à jour du registre OTA sont une fonctionnalité en attente. Actuellement, les mises à jour du registre nécessitent un flash du micrologiciel.
</Info>

Le workflow prévu pour les appareils de production :

1. Accédez à **Paramètres > Rechercher des mises à jour** sur l'appareil.
2. RADR vérifie les mises à jour du registre à partir du serveur
3. Les fichiers `registry.json` et de protocole mis à jour sont téléchargés OTA
4. La prise en charge des nouveaux appareils est disponible sans mise à jour complète du micrologiciel
